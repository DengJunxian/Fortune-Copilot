# 智运财富前端产品架构 V4

更新日期：2026-08-07

## 产品决策

客户主产品收敛为一条可直接使用的家庭理财规划流程，而不是把仓库中的全部计算、模拟和治理能力平铺给客户。基金投顾已经接入第七章，但只作为家庭规划金额的下一层说明；已有高级能力继续作为客户经理与风险人员的独立工作区。

```mermaid
flowchart LR
    A["家庭情况、客户识别与投资适当性"] --> B["资产、负债、年收入、年支出"]
    B --> C["财务报表与六项比率"]
    C --> D["理财目标与大额支出"]
    D --> E["严格八章理财规划书"]
    E --> F["第七章：动态四账户与具体产品说明"]
    B --> T["确定性财务计算"]
    T --> C
    T --> E
    C --> L["语言模型解释"]
    L --> C
    E --> L2["语言模型只解释已核验事实"]
```

## 仓库已有能力

- FastAPI 领域服务、SQLAlchemy 家庭事实库、SQLite／PostgreSQL 配置和版本化迁移。
- 家庭成员、资产、负债、收入、支出和目标的统一领域模型。
- 基于 Decimal 的资产负债表、年度现金流与家庭财务比率引擎。
- 严格八章正式规划书、HTML／PDF 导出与客户经理后续工作流。
- React、TypeScript、ECharts、Vitest 与 Playwright 工程基础。
- 三类可执行的合成客户事实，可用于观察不同生命周期的计算结果。

## 审计中发现的产品缺口

1. 原客户入口一次暴露 11 个技术性工作区，新客户无法判断从哪里开始。
2. 顶栏暴露模拟账号、能力清单和运行状态，客户需要理解系统内部设计才能使用。
3. 缺少“基础情况—报表—分析—目标—规划书”的连续表单与草稿保留。
4. 财务引擎虽然完整，但缺少一个面向普通客户的批量录入接口和简明字段体系。
5. 比率结果与模型解释未形成同屏、可核对的统一组件。
6. 原首页与客户端的可见文案偏向展示实现方法，没有围绕客户任务说话。

## 新信息架构

### 公共层

- `HomePage`：说明服务、五步流程、六项比率与三类客户案例。
- `PlanningPage`：承载整个规划旅程，没有旁路导航。
- `AppShell`：客户端只显示首页、开始规划和保存返回；内部路由才显示工作区导航。

### 规划流程层

```text
PlanningJourney
├── PlanningProfileForm
├── FinancialStatementForm
├── RatioAnalysisView
│   └── FinancialCharts
├── GoalsAndExpensesForm
└── PlanBookView
    └── ChapterSeven
        └── FundAdvisoryWorkspace
```

`PlanningJourney` 只负责步骤、草稿、请求、错误和已选案例状态；各页面组件不直接知道路由或后端实现。

### 数据访问层

- `api/wealthPlanning.ts`：客户规划批量录入、KYC、比率解释、目标写入和规划书讲解。
- `api/financial.ts`：财务分析响应契约。
- `api/formalReport.ts`：正式八章报告生成与导出。
- `api/fundAdvisory.ts`：第七章具体基金说明、渠道切换和产品资料契约。
- 页面中不散落 `fetch`，不在视图内重复计算金额或比率。

## 客户规划接口

### 创建客户规划

`POST /api/v1/wealth-planning/cases`

该接口一次接收客户基本情况和四张报表录入，在同一个事务中写入统一领域模型，随后调用确定性分析服务。响应同时返回 `household_id` 与完整 `FinancialAnalysis`，避免前端拼装计算。

### 生成比率解释

`POST /api/v1/households/{household_id}/ratio-explanations`

输入仅包含确定性引擎已验证的六项比率、报表摘要和风险标记。输出必须通过应用自有结构校验，且只能返回六个指定指标的解释。外部模型不可用时，返回确定性解释模板。

### 目标与规划书

目标写入沿用已有家庭目标接口。`POST /api/v1/households/{household_id}/plan-narrative` 同时取得确定性四账户结果与结构化章节讲解；第 1—3、5—6 章由 DeepSeek 解释已核验事实，第 7 章的关键账户金额和边界始终采用规则引擎原文。客户可在页面阅读固定八章并使用浏览器打印。

### 第七章具体产品说明

`GET /api/v1/households/{household_id}/fund-advisory` 读取已确定的四账户金额、客户风险范围和公开产品资料。接口不得反向修改规划金额。前端按“用途与金额 → 产品和风险 → 购买前确认 → 折叠的资料来源”逐层展示；无法同时满足用途、风险和渠道时，资金继续保留，不为形成满仓而放宽条件。

客户页面使用“可进一步了解”“先学习，不购买”“本次不安排”“购买前确认渠道”等状态。规则版本、求解过程、候选池、证据链和 Mock 数据只留在内部工作区。

## 状态模型

`PlanningJourney` 保存以下最小状态：

- 当前步骤与已完成步骤。
- 可编辑的客户规划草稿。
- 后端创建的家庭标识与财务分析。
- 六项模型解释、确定性四账户结果与章节讲解。
- 理财目标、大额支出与已生成正式报告。
- 当前请求状态和客户可执行的错误说明。

草稿写入浏览器本地存储，仅作为未提交内容的恢复机制。已提交事实以后端记录为准。

## 关键产品边界

- 信用卡未付是负债；信用卡额度不接收、不存储、不参与资产计算。
- 银行理财的数据用途中明确“不代表保本”。
- 最低工资变化、CPI 和目标成本变化是不同口径。
- 任何账户比例必须带分母和资金范围，不推广为家庭总资产固定配置。
- 普通家庭的基础规划不默认展示个股、杠杆和股指期货。
- “生钱的钱”先检查客户确认的 30万—100万元地区启动线；可规划金融净值按可投资金融资产减全部负债计算。未达正式启动线但正结余、多余长期资金、高息债务和适当性条件通过时，可显示不超过多余长期资金 10% 的宽基指数学习仓。
- “保本的钱”在 5%—30% 总观察带内按偏积极／中性／偏防守三档规则动态切换，客户界面显示当前参考区间和中间参考点；“生钱的钱”70% 有独立分母和适用条件，二者都不作为家庭总资产固定比例。
- 市场档位由版本化规则发布，客户和大语言模型均无权临时改写；目标、债务、保障、流动性和适当性优先于市场参考点。
- 学习仓与正式配置必须是两个前端状态；学习仓显示确定性金额、实际比例、10%上限和明确分母，70%边界不得套用于学习仓。
- 具体基金只细分第七章已经确定的金额；货币基金、债券基金、养老基金均不得描述为保本保收益。
- 客户默认不接触内部 11 个工作区。公开案例进入 `/planning`，不再跳转 `/client/advanced`。

## 验证策略

- 组件测试：家庭／个人切换、动态表格行、六项比率和八章目录。
- 合同测试：批量录入落库、财务恒等式、信用卡未付口径和模型降级。
- 浏览器主路径：首页 → 家庭情况 → 财务报表 → 六项比率 → 目标 → 八章规划书 → 第七章具体产品说明。
- 视觉验收：1440px 桌面、390px 手机，检查溢出、双层吸顶后的章节定位、五步进度同屏可读、产品卡片换行、折叠内容和主行动位置。

## 后续扩展顺序

1. 补齐客户档案修改、已有规划查询和客户经理接续入口。
2. 增加保障资料、养老金与社保信息的客户友好录入。
3. 为第七章补充交易前费用比较、持有期提醒和客户确认记录，但不在产品内直接下单。
4. 最后对接实际银行客户、账户和报表系统，不在客户端内嵌系统集成细节。
