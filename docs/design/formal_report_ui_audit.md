# 正式报告与行动闭环 UI 审计

阶段：提示词 11  
方法：`redesign-existing-projects` 的 Scan → Diagnose → Fix  
设计拨盘：客户端 `4 / 3 / 5`，顾问端 `3 / 2 / 7`，风险端 `2 / 1 / 8`

## Scan

提示词 10 结束时已有统一 token、三端外壳、客户端 11 个任务、严格八章预览、浏览器内行动勾选、顾问底稿和风险审核链。现有视觉语言是克制的深蓝／品牌红、原生表格、细边界和不同端密度，不依赖外部字体或图片。

正式报告阶段的主要断点是：预览不等于持久化报告；行动完成状态只在浏览器；顾问端不能直接读取正式八章；风险端看不到报告生成链；导出缺少统一版本、水印、数据日和渲染诊断。若直接再加一组卡片，会把方案审核链、报告链和行动链割裂。

## Diagnose

| 优先级 | 问题 | 风险 |
| --- | --- | --- |
| P0 | 客户、顾问、风险没有共享同一正式报告 ID | 投诉回放和数值一致性无法证明 |
| P0 | 行动状态不持久化，也不触发重算 | 报告完成率与客户实际操作脱节 |
| P0 | 正式目录可能被附录或来源标题扩成九章以上 | 违反八章硬约束 |
| P1 | 顾问缺少快速生成、版本和导出入口 | 不能完成面谈后的交付任务 |
| P1 | 风险端缺少父快照、哈希和治理版本 | 无法核验报告从哪次方案产生 |
| P1 | PDF 若依赖专有字体或 CDN | 离线 Demo 失败并引入授权风险 |
| P2 | 旧报告预览与正式报告可能同时争夺视觉主层 | 客户难以区分草稿、当前版和历史版 |

## Fix

### 客户端

家庭规划书改为单一主工作台：顶部只保留正式报告状态、一键生成和边界说明；生成后显示当前 Rn、数据日、哈希、八章目录、章节正文、表格、建议和引用。旧阶段预览只在尚无正式报告时作为明确标注的确定性预览降级，不冒充正式版。

行动日历继续使用五个时间分组，但每项加入持久化状态选择、原因／延期日期和保存反馈。完成、延期、不适用不使用奖励动效，保存结果明确提示已生成新的正式报告快照。

### 顾问端

正式报告面板嵌入当前客户底稿，采用不对称双栏：左侧是状态、版本、生成／重大事件重算和导出动作；右侧是严格八章目录及版本信息。目录使用有序列表，不拆成八张同质卡片。所有导出按钮显示真实失败状态。

### 风险端

生成链使用只读证据账本：每行对齐 Rn、父报告、触发原因、工作流状态、哈希和九类治理版本；链级状态明确写“已验证”或“需复核”。风险端没有生成、修改行动或导出替客户决策的控件。

### HTML/PDF

HTML 以深色封面、双栏目录、章节大分隔和窄表格构成；附录、来源和结尾使用 `support-title`，绝不使用一级章节标题。PDF 采用横向 A4、紧凑表格、页脚版本／数据日／页码／哈希和低对比水印，字体只来自系统或 Docker 的开源文泉驿正黑。

### 状态与响应式

生成、重算、下载和行动保存均有 loading、success、error；无报告时保留明确创建入口，合规前客户收到独立 PermissionDenied。桌面使用证据双栏，窄屏回落为单列；表格和目录局部滚动，不撑破文档。按钮保持 44px 触控高度，原生 select、date 和可见 label 支持键盘操作，状态不只依赖颜色。

## 验收结果

- 客户端、顾问端和风险端均读取服务端同一份报告快照或同一生成链。
- 一级章节在 Schema、HTML 和页面导航中均恰好八个；附录不参与章节计数。
- 客户行动完成会在真实 Compose 中生成 R2；风险端显示两条已验证快照。
- 1366×768 客户正式报告已保存截图回归，移动任务导航仍通过既有回归。
- PDF 32 页全部渲染检查；无字体缺失、裁切、外部资源或专有字体入库。
- 合规前 `workflow_linked` 报告不进入客户端可访问树。

本轮改造保留了现有品牌语言和组件习惯，变化集中在信息层级、共享状态和证据密度，没有引入新的装饰风格或第二套设计系统。
