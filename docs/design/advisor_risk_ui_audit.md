# 顾问端与风险端 UI 审计（提示词 10）

审计日期：2026-08-05  
方法：`redesign-existing-projects` 的 Scan → Diagnose → Fix  
设计依据：根 `DESIGN.md`、`docs/design/reference_analysis.md`、`docs/design/accessibility.md`

## Scan：现状

- 技术栈保持 React 19、TypeScript、Vite、原生 CSS 与项目自有组件，不引入新 UI 框架。
- 三端已有统一顶栏、路由、token、状态徽标、表格、抽屉、图表和 Mock 边界。
- 顾问端仅依次拼接能力清单、组合、孪生、行为与可信 AI 工作区；每个工作区各自选择家庭，没有统一客户队列、面谈准备或方案版本。
- 风险端顶部只展示七条基础禁令，随后拼接技术工作区；没有待审队列、三道闸门总览、版本链、审核动作、投诉回放或审计包。
- 后端已有 `Recommendation`、`AdvisorReview`、`CustomerConfirmation` 与 `AuditEvent`，但它们没有同一 workflow id、不可变版本和不可跳步状态机。
- 顶栏可访问三端，但没有四角色模拟账号，也无法验证按钮是否受最小权限控制。

## Diagnose：主要问题

| 严重度 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 顾问、合规、客户看到的不是同一方案版本 | 不能证明三端一致，也无法处理投诉 |
| P0 | 状态只存在于局部模块，服务端没有跳转守卫 | 客户确认或合规通过可能被绕过 |
| P0 | UI 没有权限反馈，旧 `risk` 角色只是请求头占位 | 无法验证最小权限和越权拦截 |
| P1 | 顾问端缺少客户队列、异常、冲突、面谈问题、签署和复盘 | 无法完成客户经理主任务 |
| P1 | 风险端缺少通过／阻断解释和版本、模型、Prompt、规则、知识、产品证据 | 审核结论不可核验 |
| P1 | 沟通稿没有可编辑版本与人工确认边界 | 容易把 AI 文案误当成建议决定 |
| P1 | Mock 银行数据没有统一适配层和八类来源状态 | 数据边界分散，信用卡额度误算风险上升 |
| P2 | 高密度端仍以长页面拼接为主 | 1366×768 下决策上下文断裂，扫描成本高 |

## Fix：本阶段设计方向

页面目标与设计拨盘：

| 页面 | 核心任务 | 信任要求 | 方差 | 动效 | 密度 |
| --- | --- | --- | ---: | ---: | ---: |
| 顾问工作台 | 从客户队列进入面谈底稿，完成选案、话术、提交、签署与复盘 | 每次修改显示操作者、理由、版本和来源 | 3 | 2 | 7 |
| 风险控制台 | 从待审队列检查三道闸门与十类控制，作出通过／退回／人工复核 | 阻断原因、规则、版本、哈希和请求 ID 同屏 | 2 | 1 | 8 |
| 客户确认区 | 只在合规通过后展示同一版本并逐项确认 | 不展示内部草稿；明确 Mock、风险和非保本边界 | 4 | 2 | 5 |

实施约束：

1. 保留现有顶栏与纵向页面骨架；新增一个共享方案闭环工作区，不重写既有组合、孪生、行为和可信 AI 组件。
2. 顾问端采用“客户队列表格 → 当前家庭面谈底稿 → 三方案矩阵 → 版本与动作”顺序；不使用三张营销卡。
3. 风险端采用“待审队列 → 控制矩阵 → 版本与治理账本 → 审核／投诉动作”顺序；绿色只表示已经通过，不表示预期收益。
4. 八状态使用文字步骤轨和 `aria-current`；重复的顾问编辑／提交仍生成新版本，不伪装成状态前进。
5. 沟通稿使用持久标签的 `textarea`，明确“Mock 可编辑模板，不能替代客户经理”；保存和提交分开。
6. 高风险确认、合规通过、退回、客户签署使用明确说明与原生表单控件；键盘顺序跟随视觉顺序。
7. Mock 适配层只使用“Mock”文字标识，不使用任何真实银行 Logo、色彩或界面仿制；信用卡额度显示为 `information_only`，绝不进入资产合计。
8. 1366×768 使用双列工作区，窄屏回到单列；表格局部滚动，不让文档横向溢出。
9. Loading、Empty、Error、Blocked、PermissionDenied、Degraded 均显示原因和下一步；按钮必须有进行中与结果反馈。
10. 所有色彩、间距、圆角、字体和焦点样式继续引用 `tokens.css` 与现有全局语义类。

## 人工焦点顺序

1. 跳到主要内容 → 品牌 → 三端导航 → 模拟账号。
2. 顾问端：客户队列行 → 家庭选择 → 面谈问题 → 候选选择 → 高风险人工确认 → 沟通稿 → 保存／提交。
3. 风险端：待审队列行 → 控制矩阵 → 审核理由 → 通过／退回／人工复核 → 投诉回放 → 审计导出。
4. 客户端：方案状态 → 三项确认 → 演示签署姓名 → 确认；内部草稿在合规前不进入可访问树。

## Fix 后复核

- 顾问端已经以统一客户队列为入口，实际读取异常、冲突、三候选、产品类型理由、风险流动性、8 类 Mock 接口、可编辑沟通稿、不可变版本和 12 月复盘；原组合、孪生、行为与可信 AI 工作区保留为默认收起的技术证据，不再抢占主任务。
- 风险端已经以待审队列为入口，实际显示三道闸门与十类控制、方案／规则／模型／Prompt／知识／产品／输入版本、通过／退回／人工复核、投诉回放和审计导出；阻断、预警和通过均有文字与规则解释。
- 顶栏四角色切换真实改变 API 请求头；客户端在合规前得到 PermissionDenied，合规后只收到裁剪后的当前版本。八状态步骤轨和版本账本在三端使用同一服务端数据。
- Vitest 25 项、Playwright 真实 Compose 13 项通过；三端闭环产生 V1—V9，并完成投诉回放和下载。控制台 0 error／0 warning，外部请求 0。
- 人工查看 `output/screenshots/stage10/advisor-1366.png`、`risk-1440.png` 与 `client-confirmation-390.png`：主次层级清晰，表格在组件内滚动，移动端保留当前状态和边界，未发现文档级横向溢出或品牌仿制。
- 构建仍报告主 JS 包大于 500 kB 的非阻断提示；这是既有 ECharts 与多工作区同包的性能债务，后续采用路由／工作区懒加载，不以删减审计证据解决。
